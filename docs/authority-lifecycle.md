# Authority events and lease lifecycle

Keys authenticate, grants bound authority, dispatcher policy authorizes launch, and broker leases deliver credentials. None substitutes for another. Root signature/body/reference/currentness verification belongs to dispatcher or the protected operator-installation verifier. The manager/launcher checks its receiver interlock and own facts; Keymaker authenticates exact request bytes. No new purpose, envelope, broker field or signing command is allocated here.

| Event | Required behavior and retained obligations |
| --- | --- |
| Planned launch-policy or activation-permission expiry/withdrawal | Close NEW STARTS. Worker request/refresh/renew/material may continue under protected broker policy until original-bound worker stop. No new-lease interceptor or immediate Replace is required solely by this event. It is not a security-revocation trigger. Keep the same original stop envelope and all independent lease/token debts |
| Original security detection | Close new starts/resumes. Full security qualification requires the original-detection final-material fence including in-flight request/refresh/renew; this automation is absent. Proposed manual worker stop plus operator Replace leaves delivery from ORIGINAL detection to successful Replace commit uncovered. Stop alone is not a material fence; security qualification remains closed |
| Successful broker policy Replace | Invalidates ALL old-generation leases and connections. It can invalidate earlier than original lease expiry. It never resets original security detection. Emergency Replace has no daemon prerequisite of zero leases; do not delay response waiting for expiry. Existing operator authority still applies |
| Original lease `authorized_until` | Fixed authorized ceiling, not guaranteed continued usability. Permitted renewal changes material without extending the original ceiling. Current broker policy/account/qualification checks, refusal, release and generation replacement can invalidate earlier |
| Reduce-only release and cleanup | Worker-owned release remains distinct from material delivery. A failed old-generation release remains debt and is never an acknowledgement. Process absence, lease release, lease expiry and vendor-token expiry are four different dispositions |

Ordinary safe setup is different from emergency invalidation: keep admission closed, independently prove zero active leases broker-wide, perform one protected policy replacement/reload, then obtain actual worker-UID status and adjacent foreign-UID denial. This zero-lease precondition is an operator setup obligation, not a daemon reload promise. Status establishes neither no active leases nor manager generation/currentness; it must not become a token-producing verification lease. Unknown reload/store effects stay held; a selected old policy pointer does not prove healthy rollback.

No limited canary is qualified by manual stop plus Replace. It requires explicit owner acceptance of the uncovered original-detection-to-commit interval, exact owner Signer approval, and every unchanged native/setup/qualification/quiet-period gate. New automatic event-to-final-material fencing is separate broker work requiring a published contract and native qualification. Delivered vendor tokens do not acquire instantaneous remote revocation.

For security revocation, running affected work must reach independently confirmed qualified narrowing or complete account-wide quiet absence within five minutes of original detection, with every shorter original bound retained. Detector latency and affected-set completeness are separate requirements. Retry, restart, reboot, lease renewal, new evidence or late receipt cannot reset a clock, replenish a start debit or erase uncertain effects, claims, lease/token/output/custody/stop debts. Authenticated status/observe/reconcile and authorized reduce-only stop must remain reachable under holds while their retained authority and integrity remain intact.
